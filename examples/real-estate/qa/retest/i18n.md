## NEW findings

### NEW-i18n-1 A translator can't start a translation
- Severity: medium
- Area: editor UX
- Where: `/admin/cms/entries/34/edit` as Dewi (translator)
- Steps: 1. Sign in as Dewi. 2. Open any entry that has no Indonesian translation yet (for example the journal post "Lumina Estates opens a new office in Canggu", before this re-test).
- Expected: A "+ Bahasa Indonesia" button to add the language and translate it. The default `translator` role is documented as "writes the other languages".
- Actual: The language bar shows only "English (main)". The add button needs `can.create` (`LanguageBar canAdd={can.create …}`), which translators don't have. Dewi can only work on translations an editor or admin has already started. In this re-test Ayu had to add the language before Dewi could translate.
- Screenshot: (the language bar with only "English (main)", captured during the run as a probe)
- Note: Either let `cms.entries.translate` add a non-main language (as a draft), or say in the role docs and the Guide that an editor must add the language first.

### NEW-i18n-2 What visitors read outside entries can only be translated by admins
- Severity: low
- Area: i18n
- Where: Blueprints (field *In other languages*), Collections/Taxonomies (*Title in …*), Forms (*Thank-you message in …*), Menus, Settings → Site (description)
- Steps: As Dewi, look for any of these screens.
- Expected: A translator can translate the visitor-facing words of forms, menus and listing titles.
- Actual: They all sit in Structure or Settings screens that a translator can't open. Form labels and option labels need blueprint edit rights, so an admin has to type every Indonesian label.
- Note: This may be acceptable for small sites, but it should be said in the translator role's description.

### NEW-i18n-3 Menu items: an English-only custom label wins over the target's translated title; misleading placeholders
- Severity: polish
- Area: admin UI
- Where: Menus → Main; `/id` navigation and footer
- Steps: 1. A listing item with the custom English label "Team" and no Indonesian label. 2. Give the Agents collection the Indonesian title "Tim". 3. Open `/id`.
- Expected: "Tim" (the translated title of the target), or a placeholder that says what will show.
- Actual: "Team", and the footer's "Our team" likewise. The Indonesian label placeholder says "Bahasa Indonesia: as English", which is true but hides the fact that the translated title is never used once there is any custom label. Also, the *Filters* input on every listing item shows the placeholder `listing_type=for-sale`, even on Neighbourhoods, Agents and Journal, which have no such filter.
- Screenshot: `qa/retest/screenshots/I18N-3-menu-editor-after.jpg`

### NEW-i18n-4 Site description per language is a "code: text" textarea, unlike every other translated setting
- Severity: polish
- Area: admin UI
- Where: Settings → Site → *Description in other languages*
- Actual: One textarea where you type `id: …` lines. Collections, taxonomies, forms, media and menu labels all have a labelled input per language ("Title in Bahasa Indonesia").
- Screenshot: `qa/retest/screenshots/I18N-12-site-description-in-id.jpg`
- Note: Use the same per-language input as the other translated settings.

### NEW-i18n-5 Docs write `Site::urlIn()` like a static call
- Severity: polish
- Area: docs
- Where: `packages/cms/docs/site.md`, line 15
- Actual: The docs give "`Sunrice\Cms\Site\Site::urlIn($translation, $locale)` gives the page to link to". The method is an instance method, so calling it as written throws "Non-static method … cannot be called statically". In the same sentence `termUrlIn` is written correctly as `app(Site::class)->termUrlIn(...)`.
- Note: Write `app(Site::class)->urlIn(...)`.

### NEW-i18n-6 Example property gallery lightbox still uses single-language alt
- Severity: low
- Area: site
- Where: `examples/real-estate/resources/views/cms/properties.blade.php:95` (and the Lumina copy)
- Actual: The lightbox's `data-items` use `'alt' => $m->alt ?? ''`, so Indonesian visitors get English alt text in the lightbox. The image partial already uses `altIn()`.
- Note: Change it to `$m->altIn()`.

### Environment note (not a Sunrice bug)
The pre-re-test "structure re-import" took `database/structure.json`, an older file than `pre-retest-structure.json`. It overwrote the menus:
- Every Indonesian menu label was lost.
- The main menu lost About (with Our story), Services and Contact.
- The footer lost Services, Sell with us and Contact.
- The legal menu is now empty.

I restored only the main-menu items I worked on for I18N-3 (Dijual, Disewakan, Vila, Tim). Restoring the rest from `pre-retest-structure.json` (menus section) is a decision for whoever owns the site.

## What works well now
- Indonesian visitors see the whole catalogue: listings, term pages, search and filter counts include untranslated entries, linked at `/id` addresses with the fallback note.
- Forms are fully Indonesian on `/id`: labels, options, errors (named by their Indonesian labels) and thank-you messages, while English stays untouched.
- Filter links work across languages. English or Indonesian slugs both filter, the switcher keeps filters, and the menu's *Listing* link with Filters gives one item for both languages.
- Translations are consistent and easy to enter: collection, taxonomy, form, media and term translations each have their own clearly labelled input, and language names match everywhere.
- Dates of new translations follow the entry, and Status → Date fixes older ones in two clicks.
- The main-language switch is safe: a failure at any step leaves the content as it was.
