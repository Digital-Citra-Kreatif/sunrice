## New findings

### NEW-security-1: The invitation and "Email a password link" mail is built from the request's Host
- Severity: low
- Area: security
- Where: `packages/admin/src/Notifications/PanelInvitation.php:42` (`url(route('sunrice.admin.password.reset', …, false))`); Users → New user → "Email an invitation", and the Users row action "Email a password link"
- Steps: 1. Run `qa/scripts/retest-security-invite-url.php`, which builds the links during a request for `http://evil.example/admin/users`. 2. The invitation comes out as `http://evil.example/admin/reset-password/TOKEN?email=…`, while `AppUrl::route()` gives `http://127.0.0.1:8200/…`.
- Expected: like the reset mail since SEC-1, the link (which carries a working reset token) is built from `APP_URL`.
- Actual: it's built from whatever host the admin's request came in on. The mail is sent during that request, not from the queue.
- Note: An attacker can't easily use this: with a forged Host the admin's session isn't valid (the request is redirected to login). It does matter when admins reach the panel through a second hostname or a proxy that passes Host through. Fix: one line, use `AppUrl::route()` as `ResetPanelPassword` does.

### NEW-security-2: `cms_render_page`'s "public pages only" check is bypassed with percent-encoding
- Severity: low
- Area: security / API
- Where: `packages/cms/src/Ai/RenderPage.php`; MCP tool `cms_render_page`
- Steps: 1. With a read-only token, call `cms_render_page {"path":"/admin"}` → refused. 2. Call `{"path":"/%61dmin"}` → `status 302, redirect http://127.0.0.1:8200/admin/login`, so the panel route was reached. 3. `{"path":"/%5Finertia/devtools"}` → 404 today, only because DevTools are off.
- Expected: the path is decoded and normalised before the panel, developer-tools and MCP prefixes are checked.
- Actual: the prefix check runs on the raw path, and routing decodes it afterwards.
- Note: No data is exposed today: the render runs as a guest, and Inertia DevTools are now off by default. If an app turns DevTools back on, a read-only token could read `/_inertia/devtools/entries` through `/%5Finertia/…`, which is what SEC-4 closed.

### NEW-security-3: An image with `<?= … ?>` appended passes the new PHP-in-image check (media library and form uploads)
- Severity: low
- Area: security
- Where: `packages/admin/src/Media/FileContent.php` (`containsPhp()` searches only for `<?php`); used by `UploadMedia` and the CMS `FileField`
- Steps: 1. Make a valid 40×30 JPEG and append `<?= \`id\` ?>`. 2. Upload it as Budi in Media → accepted (media 13, stored on the **public** disk with the code intact). 3. Send it as a photo on the valuation form → "Thank you…", stored (submission 16). 4. The same JPEG with `<?php echo 1; ?>` is refused in both places.
- Expected: the polyglot is refused like the `<?php` one. Short echo tags `<?=` always run in PHP 8, whatever `short_open_tag` says.
- Actual: accepted and stored unchanged.
- Note: The risk is still only on a misconfigured server that executes files in `storage/`. That's the same scope as SEC-12, but the new check promises more than it does. Fix: also look for `<?=` (and `<?` followed by whitespace when `short_open_tag` is on), or re-encode raster uploads. I deleted the test media and submission.

## What works well now
- Reset links, security alerts and CMS notification mails ignore a forged Host. In production `trustHosts()` answers a forged Host with 400.
- The login form gives one generic answer, and the forgot-password limit (5 a minute, 20 an hour) logs the block and sends an alert.
- Translators are kept out of every shared setting and every entry action (settings, order, date, duplicate, trash, homepage), and shared field values can't be changed through a translation's draft.
- Uploads: a text file named `.jpg` and a JPEG with `<?php` are refused with clear messages, and the polyglot is logged as a blocked upload.
- Turning on two-factor while mail goes only to the log is refused with an explanation, and the login code is no longer in the subject.
- The AI access page warns about full tokens and personal data, `cms_write_template` is no longer advertised where it would only refuse, rendered pages use APP_URL, the SEO audit reads the real head, reorders log only real changes, and `sunrice:ai-token` refuses when AI access is off.
- Seeded roles keep the admin's edits across `sunrice:roles`, `purged` triggers the mass-delete alert, and a dashboard widget without a guard fails at registration.
