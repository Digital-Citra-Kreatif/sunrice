# Changelog

## 0.2.0 (2026-10-25)

### All changes

- **Templates picked on the listing and index pages**: a collection's **Listing page template** and a taxonomy's **Index page template** could be set only under Structure, so they were hard to find from the page they change. The listing page editor (**Entries → ⋮ → Listing page**) and the index page editor (**Terms → ⋮ → Index page**) now have the same **Template** choice as an entry's Page settings, in a **Page settings** card beside the page's fields as in the entry and term editors (a page without fields of its own says so in a card that lines up with it, with **Choose a listing blueprint** or **Choose index page fields** taking those who may to that setting on the collection's or taxonomy's form): the views that exist, **Automatic**, any view name typed in, the file in use and **How is it chosen?** with the files tried for that page. It is saved with the page's fields by its **Save**, for those who may change the collection (`cms.collections.update`) or the taxonomy (`cms.taxonomies.update`); others see it greyed out, and a save that sends it without that permission answers 403. The index page template is still one per taxonomy, for the shared index page and every collection's. Under Structure, the four template settings (**Entry template**, **Listing page template**, **Term page template**, **Index page template**) were text boxes; they're now the same kind of choice: **Automatic** (empty) first, then the views that exist (those in `cms/` first, layouts, partials and the like left out), with **Other view…** for any view name typed in, checked as before. The line under the listing and index page templates says which file is used ("Uses cms/collections/index.blade.php."). The collection form's **Edit listing page** link shows whenever the collection has a listing page, not only with a listing blueprint. The listing page editor's back link and breadcrumbs (Collections › the collection › Listing page) go to the collection's settings for those who may change them, else to its entries as before; the index page editor's (Taxonomies › the taxonomy › Index page) to the taxonomy's settings, else to its terms. New internal `TemplateHelp::select()`. `TemplateLookup::listing()` and `index()` take `own: false` for the views tried without the setting (internal); new internal actions `SaveListingTemplate` and `SaveIndexTemplate`. See [Templates](packages/cms/docs/site.md#templates).
- **Docs: turning the panel's own parts off**: [The panel and plugins](packages/admin/docs/panel.md#turning-built-in-parts-off) gathers the switches that were spread over their pages: `$panel->aiAccess(false)`, `ai.enabled`, `$panel->mediaLibrary(false)`, `userResource(null)` and `roleResource(null)`, `withoutWidgets()` and `activity.enabled`, and says that the Guide, Developer docs and Activity log are hidden through their permissions (super admins always see them).
- **The terms list no longer labels every use of every term**: to warn before trashing or deleting a term, a taxonomy's **Terms** list read every reference to every term and gave each one a label, a link and its field's label on every load (on a taxonomy with 300 terms and about 2,000 uses, some 375 of its 486 ms), though the confirmation names only the first five. Each term now carries its first five uses' labels (`usedBy`, in the same order as before) and how many it has in all (`usedByCount`), counted with one grouped query, so the page reads the same queries however many uses there are (100 terms with 20 uses each: 245 → 95 ms in a test). The confirmation's "… and N more" and the force flag of **Permanently delete** follow `usedByCount`. The entry and term editors still list every use. `References::usedByMany()` takes an optional limit, and the new `References::usedByCount()` counts (both internal); uses from a source that no longer exists aren't counted, as they weren't listed.
- **Faster admin lists on big sites** (a performance pass on a site with 5,000 entries in three languages, 900 terms, 2,000 files, 3,000 comments and 20,000 activity rows): a taxonomy's **Terms** list worked out each term's page with two queries per term (635 queries for 300 terms, 1,173 for 574), now a fixed 25; **Comments** loaded each comment's entry and collection again (69 queries for a page of 25, now 20), and the AI tool `cms_list_entries` each language's entry (53, now 19). New indexes on `sunrice_entry_translations` (in its create migration; 0.1 sites start afresh anyway): `(collection_id, locale, published_at)` and `(collection_id, locale, draft_title)` for the entries lists in their default orders, so a page of a 2,000-entry collection no longer sorts the whole collection (40th page: 103 → 14 ms of SQL), and `(locale, updated_at)` for the entries picker's most recently edited (32 → 2 ms). The entries list's term filters read plain rows instead of models (70 → 8 ms for 900 terms), Settings → Site's homepage choices and "Used by" (the entry and term editors, the terms list) read only the titles they show instead of whole entries (133 → 24 ms of SQL), "Used by" skips its queries for kinds of source that aren't there, and the sidebar's collection, taxonomy and form handles are read from the cache once per request (`Cache::memo()`), not four times. Tests lock in the query counts.
- **A lighter sitemap on big sites**: built afresh (not cached), `/sitemap.xml` for 12,000 addresses (5,000 entries in three languages, plus terms) peaked at 100 MB of memory, close to a 128 MB `memory_limit`, and took 4.5 s; now 20 MB and 3.2 s, with the same XML byte for byte. It reads only the columns an address needs (no fields, drafts or search text) for entries, terms and their other languages, reads "Hide from search engines" in SQL (on SQLite, MySQL/MariaDB and Postgres) instead of decoding every page's fields for it, makes the alternate-language links once per entry or term rather than once per language, and lets go of each chunk of 500 before the next. Pages whose URL pattern takes an entries field (`/projects/{project}/{slug}`) still read their fields. The page cache's preload list (`PreloadCache`) reads the same way (57 → 34 MB). Tests lock in the query count, the columns read and the output.

- **Migrations consolidated again; upgrading from 0.1 needs a fresh database** (breaking): the 0.2 columns are made by the create migrations that make their tables, and the migrations added since 0.1.0 are removed. Panel `2026_10_23_000001_add_weak_password_to_sunrice_account_security_table` is folded into `2026_01_01_000005` (`weak_password`). CMS `2026_10_23_000001_add_entry_terms_columns` is folded into `2026_02_01_000003` (`sunrice_collection_taxonomy.single`) and `000002` (`sunrice_entries.draft_terms`, `sunrice_revisions.terms`), and `2026_10_23_000010_add_live_columns_to_entry_translations` into `2026_02_01_000002` (`live_version`, `live_updated_at`). The data-only upgrade migrations do nothing on a new database and are removed: `2026_10_23_000002_move_terms_fields_to_entry_terms`, `2026_10_24_000001_attach_taxonomies_from_terms_fields`, `2026_10_24_000010_record_seo_settings_media`, `2026_10_25_000001_give_globals_configure_permission` and `2026_10_25_000002_give_menus_configure_permission`. `cms.globals.configure` and `cms.menus.configure` reach the `administrator` role through `sunrice:roles` (its `*`), as every permission does. A fresh install gets the same tables, columns, indexes and foreign keys as before. On MySQL, `weak_password` is now the table's last column (it was after `signed_out_at`). This is a deliberate exception to "never modify a released migration" before 1.0: a 0.1 database can't be migrated to 0.2, and must be rebuilt with `php artisan migrate:fresh`, which drops every table, the app's too. To keep a 0.1 site's content, make a starter of it on 0.1 (`sunrice:make-starter`, which brings the media files along) and install it with `sunrice:starter --path=` after the rebuild. Settings, users, roles, revisions, form submissions, comments and the activity log aren't carried over: keep a database backup. See [Upgrading](docs/upgrading.md#keeping-a-01-sites-content).
- **Saving a menu's links without `items` no longer empties it**: `PUT /admin/cms/menus/{handle}/links` took a body with no `items` (or a non-array one) as an empty tree and deleted every link. `items` is now required (present and an array): a missing or non-array one answers 422 and leaves the links as they are, while an explicit `[]` still clears the menu. The AI tool `cms_save_menu` already refused a missing `items`; a test now says so.
- **Permanently deleting from the trash says so on the button**: the confirm dialog for a file's **Permanently delete** (its details and the media library's bulk bar) and for a resource's records in the trash (a row and the bulk bar) said "Continue"; its button now reads **Permanently delete** (Indonesian *Hapus permanen*). The panel's `useConfirm()` takes an optional button label (internal). The CMS's trash confirms (entries, terms, comments, submissions) already said **Delete**.
- **Upgrade guide**: the 0.2 notes say that a `config/sunrice-admin.php` published on 0.1 still has a comment above `security.headers.csp` saying a Content-Security-Policy is sent "only when set here", which is now wrong: the panel sends one by default, and `security.headers.csp` replaces it as a whole.
- **No block, search page or unsubscribe page as a page's template**: `cms.blocks.hero` (a flexible block's view), `cms.search` and `cms.comment-unsubscribe` (the views the CMS renders by name for the search page and a reply email's unsubscribe page) were accepted as an entry's or a term's template and listed in the **Template** choice, and a page set to one answered 500, since they need variables an entry's page doesn't have. `SaveEntrySettings::NOT_PAGES` now has `blocks`, and `NOT_PAGE_NAMES` `search` and `comment-unsubscribe` besides `layout`, so `allowed()` refuses them (any view in a `blocks` folder or named so, prefixes or not), a stored one is ignored and the Template choice leaves them out; the search and unsubscribe pages still render with `cms.search` and `cms.comment-unsubscribe`. The message names them too ("Use a view under cms., pages., not under layouts, partials, components, blocks, … nor named layout, search, comment-unsubscribe, like cms.landing.", in Indonesian too). See [Templates](packages/cms/docs/site.md#templates).
- **`sunrice:starter` asks to choose the homepage only when there is none**: it always ended with "Done. Choose the homepage and check Settings → Site in the admin.", even when the starter had set the homepage (the Blog starter does) or the site had one; then it now says "Done. Check Settings → Site in the admin.".
- **`when()` and `unless()` on entry queries**: `Cms::entries()` (`EntryQuery`) uses Laravel's `Conditionable`, so a filter applies only when a value is given: `Cms::entries('homes')->when($request->integer('max_price'), fn ($q, $max) => $q->where('price', '<=', $max))`. See [Querying entries](packages/cms/docs/site.md#querying-entries).
- **Data for JavaScript** (`toData()`): plain arrays of what the site shows, for scripts on its pages (maps, galleries, cards, "load more") and small JSON routes an app writes itself; no routes or API of its own. New `@api` methods: the panel's `Media::toData(?string $locale = null)` (`id`, `url`, `alt`, `title`, `caption`, `mime`, `type`, an image's `width` and `height`, `sizes` as `{name: {url, width, height}}` and `srcset`, with the same URLs as `url()` and `srcset()`; in the trash `url: null` and no sizes); the CMS's `EntryTranslation::toData(array $fields = [])` (`id` of the entry, `locale`, `title`, `slug`, `url`, `collection`, `published_at` in ISO 8601, `parent_id`, `terms` by taxonomy handle, and `fields` with only the fields named, converted from `values()`: media, linked entries (without their fields) and terms as their data, dates in ISO 8601, groups, repeaters and flexible blocks with the same conversion inside, handles the blueprint doesn't have left out), so it's the live version (a preview's draft) in the page's language with the main language standing in; `Term::toData(?string $locale = null)` and `TermTranslation::toData()` (`id`, `taxonomy`, `locale`, `title`, `slug`, `url`, `parent_id`); and `Cms::toData($items, $fields = [])` for a list of them (a collection or array gives a list, a paginator `{data, meta: {current_page, last_page, per_page, total, next_url, prev_url}}`). Entries from `Cms::entries()` share their `HydrationContext`, so a list costs a fixed number of queries. Eloquent's `toArray()` and `toJson()` are unchanged. See [Data for JavaScript](packages/cms/docs/site.md#data-for-javascript) and [Media](packages/admin/docs/media.md#uploading-from-code). [Filtering with JavaScript](packages/cms/docs/site.md#filtering-with-javascript) shows filtering in the browser or through a JSON route of the app's.
- **Published config files get the keys added since they were published**: the panel and the CMS merged their config with Laravel's `mergeConfigFrom()`, which merges only the top-level keys, so a `config/sunrice-admin.php` or `config/sunrice-cms.php` published on 0.1 (which has `auth`, `media`, `security` and `site`) had none of the keys added under them since, and their env variables did nothing: `security.csp.*` (`SUNRICE_CSP_ENABLED`, `SUNRICE_CSP_REPORT_ONLY`, `SUNRICE_CSP_REPORT_URI`), `auth.password_uncompromised` (`SUNRICE_PASSWORD_UNCOMPROMISED`), `auth.strong_passwords`, `auth.password_min`, `media.trash_disk`, `media.trash_directory`, `site.csp.*` (`SUNRICE_SITE_CSP_*`), `site.custom_code` (`SUNRICE_SITE_CODE`) and `site.lazy_sessions` (`SUNRICE_LAZY_SESSIONS`). Both now merge at every depth with the new `@api` `Sunrice\Admin\Support\PackageConfig::merge($app, $path, $key, whole: [...])`: a missing key gets the package's default and `env()` read, a key the app set keeps its value (`null` and `[]` included), lists are replaced as a whole, never merged index by index (`['cms.']` stays `['cms.']`), maps of the app's own keys named in `whole` too (`locales`, `media.image_sizes`, `security.csp.sources`, `ai.commands`; `locale_names`, `locale_prefixes`, `site.headers`, `site.csp.sources`), and nothing is merged while the configuration is cached. Plugins with a config file of their own should use it too. See [Configuration](packages/admin/docs/configuration.md), [Writing a plugin](packages/admin/docs/plugins.md#its-config-file) and [Upgrading](docs/upgrading.md).
- **Docs and AI tool texts catch up with the code** (docs audit): `cms_get_template_guide` gives the real rule for a page's own template (a view under `sunrice-cms.site.template_prefixes`, by default `cms.` and `pages.`, never one under `layouts`, `partials`, `components` and the other excluded folders, a view named `layout`, `_` files or a package's view; it said they must start with `cms.`), says that `cms_read_template`, `cms_write_template` and its `templates` list cover only `resources/views/cms`, and tells agents to give inline `<script>` and `<style>` `nonce="{{ cms_nonce() }}"` under the site's Content-Security-Policy (inline `onclick` never runs). `cms_get_template_guide`, `cms_read_template`, `cms_field_types` and `cms_get_blueprint` name the permission they need as **View blueprints** (`cms.blueprints.view`; they said "Manage blueprints"). `cms_field_types` says textarea, code and link fields take a placeholder too, and `manage_media` that trashing a file takes it offline (its links stop working, `url` and `thumbnail` are null until it's restored). Docs: the 0.2 upgrade notes add `MakeStarter::LANG`'s removal, `sunrice:translate`'s new default parts (listing and index pages and site texts, saved live) and exports keeping drafts as drafts; `cms.blueprints.*` and `cms.fieldsets.*` replace the `cms.blueprints.manage` that never existed, and per-taxonomy permissions are `cms.terms.{taxonomy}.view|create|update|delete`; starters and `--settings` carry Settings → SEO's values too; `cms_nonce()` is listed with the template functions; the user guides describe the term picker, the editor role without form submissions or menus' and global sets' settings, trashed media going offline, **Taxonomy index** menu links and code fields' placeholder.
- **A strict Content-Security-Policy for the panel, an optional one for the site** (finding F-033). Every panel page now sends `Content-Security-Policy` (on by default; `sunrice-admin.security.csp`: `enabled` / `SUNRICE_CSP_ENABLED`, `report_only` / `SUNRICE_CSP_REPORT_ONLY`, `report_uri` / `SUNRICE_CSP_REPORT_URI`, and `sources` per directive): `default-src 'self'`, scripts and styles from the panel's origin or with a new nonce on every request (`Vite::useCspNonce()`, which the admin layout's inline scripts and styles, Vite's tags and a new `<meta property="csp-nonce">` carry), `style-src-attr 'unsafe-inline'` for the `style=""` attributes React and Radix set, images from the panel, `data:`, `blob:` and the media disk's origin, `connect-src 'self'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'` and `frame-ancestors 'none'`; `APP_URL`, `ASSET_URL`, plugin bundles' and the branding font's origins and the Vite dev server (with its websocket) are added when they apply. The `<style>` elements the panel's libraries create from script (toasts, the progress bar, dialogs' scroll lock, the editors) get the nonce from the layout's first script. JSON, files and the framework's debug error page get no policy. `SUNRICE_CSP` (`security.headers.csp`) is still a whole policy of your own, sent as is instead. `AdminAssets::tags()` now gives Vite's tags the request's nonce (they had none, its `Vite` instance being its own). New `@api` `Sunrice\Admin\Security\ContentSecurityPolicy` (`make()`, `add()`, `addMany()`, `nonce()`, `toString()`, `origin()`, `mediaOrigin()`) builds policies source by source and drops sources that could break the header; `Captcha::cspSources()` says what the captcha's widget needs, and its script carries the nonce. The site's policy (`sunrice-cms.site.csp`, off by default: `SUNRICE_SITE_CSP_ENABLED`, `_REPORT_ONLY`, `_REPORT_URI`, `nonce`, `sources`; new `@api` `Sunrice\Cms\Site\SiteCsp`) is the same idea with `frame-ancestors 'self'`, the captcha's sources when it's set up and the app's Vite dev server: the CMS's plain pages' `<style>` blocks have the nonce, `<x-sunrice-cms::code>` adds it to Site code's `<script>` and `<style>` tags (`SiteCsp::withNonce()`), templates print it with the new `cms_nonce()`, and `nonce => false` leaves it out for snippets that need `'unsafe-inline'`. With the page cache on, kept pages are stored with a placeholder for the nonce, in the page and its header, and served with the serving request's (new `@api` `Sunrice\Cms\Site\CspNonceReplacer`, added to `responsecache.replacers` like `HoneypotReplacer`), so every visitor still gets a new nonce. HSTS stays the web server's. See [panel security](packages/admin/docs/security.md#content-security-policy), [site security](packages/cms/docs/site.md#content-security-policy), [Whole pages](packages/cms/docs/caching.md#whole-pages) and [Upgrading](docs/upgrading.md).
- **Move to trash takes a file offline** (F-027): a file in the media library's trash could still be downloaded at its `/storage/media/…` URL until it was permanently deleted. Moving it to the trash (the page, bulk, the AI `manage_media` tool, `TrashMedia` or `$media->delete()`) now moves its original and every size off the public disk to a private one, new config `media.trash_disk` (default `local`, `storage/app/private`) under `media.trash_directory` (`sunrice-media-trash/`), at the same paths; restoring moves them back, so links work again; **Permanently delete** (and `DeleteMedia`) removes them wherever they are. Moves are all or nothing: if a file can't be moved, nothing changes and the page says why (new `@api` `Sunrice\Admin\Media\MediaFilesNotMoved` from code). Sizes a queued `GenerateImageSizes` job makes for a file trashed meanwhile are deleted, not left public. In the trash a file shows a placeholder and has no link (`url` and `thumbnail` are `null` in the page's and the AI tools' data), and making a starter (`sunrice:make-starter`) leaves trashed files out. New command `sunrice:media-trash-offline` takes files trashed before this version offline (see [Upgrading](docs/upgrading.md)). See [Media](packages/admin/docs/media.md#the-trash).
- **Permanently deleting a file warns of broken links only when it's used**: the dialog said "Pages using it will show a broken link." for every file; a file nothing uses now says "Nothing uses it. This can't be undone." (in Indonesian too; the page's items in the trash carry it as `deleteWarning`).
- **Editors edit menus' links, not their handles** (follows F-062): `cms.menus.update`, which the default `editor` role has, let an editor rename a menu's handle on its **Settings**, and templates find menus by handle (`Cms::menu('main')`), so renaming `main` emptied the site's navigation. A menu's Settings (title, handle; `PUT /admin/cms/menus/{handle}`, and agents' `save_record` on `menus`) now also take the new `cms.menus.configure` (*Change menus' titles and handles*, under Menus in Roles), which the `editor` role doesn't get: without it the links page shows no **Settings** link, the menus list no edit action, and Settings answers 403. Editing the links (`/admin/cms/menus/{handle}/links`, `cms_save_menu`, `cms_reorder`) still takes `cms.menus.update` only; creating and deleting menus still take `cms.menus.create` and `.delete`. The `administrator` role has it (`sunrice:roles`), editors don't. New `MenuResource::configures()` (internal). See [Menus](packages/cms/docs/menus.md#setting-up-and-editing).
- **Editors edit globals' values, not their sets' handles and blueprints** (F-062): `cms.globals.update`, which the default `editor` role has, let an editor rename a global set's handle or swap its blueprint on its **Settings**, and templates find sets by handle (`Cms::global('footer')`), so renaming `footer` emptied the site's footer. A set's Settings (title, handle, blueprint; `PUT /admin/cms/globals/{handle}`, and agents' `save_record` on `globals`) now also take the new `cms.globals.configure` (*Change global sets' titles, handles and blueprints*, under Globals in Roles), which the `editor` role doesn't get: without it the values page shows no **Settings** link and Settings answers 403. Saving values (`/admin/cms/globals/{handle}/values`, `cms_save_globals`) still takes `cms.globals.update` only; creating and deleting sets still take `cms.globals.create` and `.delete`, which editors never had. The `administrator` role has it (`sunrice:roles`), editors don't. New `GlobalSetResource::configures()` (internal). See [Globals](packages/cms/docs/globals.md#setting-up).
- **Term names in the page's language**: `Term::title()` and `Term::translation()` without a language gave the main language's (English) title while `Term::url()` used the page's, so `/id/…` and `/zh/…` pages showed "News" linking to `/id/topics/berita`. Both now default to the language of the page shown (`Locales::current()`, as `url()`), falling back to the main language's when the term has no translation there; a language given (`title('en')`) still wins. The admin's uses (the term picker's labels and parents' tooltips, the terms list's fallback title, the menu editor, the activity log's names) pass the main language, so they don't follow the panel's language. See [Taxonomies](packages/cms/docs/taxonomies.md#terms-fields) and [Upgrading](docs/upgrading.md).
- **Typing HTML in the code editor closes no tags for you**: CodeMirror's HTML support added `</div>` as soon as `<div>` was typed (and completed `</` too), so someone typing the whole `<div>Hi</div>` saved `<div>Hi</div></div>`. HTML is now loaded with `autoCloseTags: false` (`HTML_OPTIONS` in `code-editor-languages.ts`); no language brings `closeBrackets`, so a typed `)` or `"` isn't doubled either.
- **Code fields show as code on the site**: pages get `$code` (their code fields, handle => language, `Code::language()`), and the starter templates' and the Blog starter's `cms/partials/fields.blade.php` (blocks too) and the CMS's plain pages print those fields with `<x-sunrice-cms::code-block>` instead of an escaped `<p>`. - **No layout or partial as a page's template, prefixes or not**: with `sunrice-cms.site.template_prefixes` set (the default, `['cms.', 'pages.']`), a template under a prefix was accepted whatever it was, so `cms.partials.card`, `cms.layouts.app`, `cms.emails.welcome`, `cms._private` or `pages.partials.x` could be an entry's or a term's page and render publicly. `SaveEntrySettings::allowed()` now refuses, with or without prefixes, a view with a `NOT_PAGES` folder at any depth or a part starting with `_`, and the site's layout, `cms.layout` (new `SaveEntrySettings::NOT_PAGE_NAMES`: any view named `layout`), a package's view under a prefix included (`sunrice-cms::components.seo`); a stored one is ignored, and the **Template** choice leaves them out. - **Language switcher links carry no tracking parameters from kept pages**: a listing's or term page's links in other languages (`Cms::localeUrls()`, `<x-sunrice-cms::language-switcher>`) copied the whole query string, and with the page cache on the page kept from `/blog?utm_content=…` was served for `/blog` with those links. With the page cache on, they now keep only the parameters kept pages are told apart by (`PageCacheQuery::query()`: `page`, `cache.query` and Settings → Cache's); without it, the query string as before.

Whether it's on is now part of the kept pages' name (`PageCacheProfile::useCacheNameSuffix()`), so switching it either way serves pages rendered with the switch as it is.

## 0.1.0 (2026-10-22)

The first release. Until 1.0, APIs may still change between versions; every change is recorded here.

**Highlights.** The panel (`sunrice/admin`) and the CMS (`sunrice/cms`) are rebuilt as two packages: a panel framework for any Laravel app, and the CMS as a plugin that uses only the panel's public (`@api`) API. The panel brings sign-in with two-factor login, users and roles with strict rank, resources, React pages through `@imajiner/admin-sdk`, settings, branding, a dashboard with widgets, a media library, an activity log with security events and email alerts, edit locks, AI access over MCP, and Help pages with the developer docs and a user guide in English and Indonesian. The CMS brings collections and entries with drafts, scheduling, revisions and per-entry blueprints, blueprints and fieldsets, taxonomies with term pages, globals, menus, forms, comments, multilingual content with outdated-translation badges and machine translation, and the site side: URLs, templates and components, SEO and structured data, sitemaps, redirects, search and caching. See `docs/README.md`.

### All changes

- **Admin performance fixes**: the Users list no longer hashes a random password for every row (`RegisteredResource::recordKey()` reads the key name from a plain model instead of `Resource::newRecord()`, which `UserResource` uses to give a new user an unguessable password; a relation field's option search doesn't call it either), about 230 ms a row before. The CMS's entry list no longer runs two queries per row for entries in more than one language. The panel's main script is 368 kB (118 kB gzipped) instead of 786 kB (244 kB): the admin layout and the runtime plugins use (`window.Sunrice`, now installed before the first plugin bundle loads) are their own chunks, and `DatePicker`, `MediaPickerInput`, `SortableList` and `SortableHandle` (in `@imajiner/admin-sdk/ui` too) and the fields of a confirmation dialog load the first time they show. Instrument Sans is built into the panel's CSS (`resources/fonts`, SIL Open Font License) instead of loaded from fonts.bunny.net: `sunrice-admin.font.stylesheet` is `null` by default (an app that published the config keeps loading Bunny Fonts until it sets it to `null`), and choosing Instrument Sans in Settings → Branding loads no stylesheet; the CSP example in the security docs no longer needs `fonts.bunny.net`. Publishing the assets (`sunrice:assets`, and `vendor:publish` for plugin bundles with `publishedFrom()`) writes a `.gz` copy of every script and stylesheet (`gzencode`, level 9), and a `.br` one when PHP has the `brotli` extension; new `PluginBundle::publishedPath()`; the installation docs show how to serve them with long cache headers. The browser smoke test (`tests/Browser/smoke.mjs`) finds the editors by their current addresses (by collection, taxonomy and handle). On the site, `SiteCache` reads each value from the cache store once per request and what nearly every page reads (language routes, blueprints, fieldsets, global sets) in one read; blueprints and a language's menus are cached under one key each (`records:blueprints`, `menus:…`): with the database cache store a page makes 4 to 6 cache queries instead of 10 to 13.
- **Migrations consolidated** (breaking for development databases): each table now has one create migration holding its final schema (every column, index and foreign key the later migrations added), and the add, change, index and backfill migrations are gone. The schema is the same on SQLite, MySQL and Postgres (the full-text index for site search is made by `2026_02_01_000002_create_sunrice_collections_tables`); new taxonomy attachments still get term pages and an index page by default. - Plugin styles are prefixed (`prefix(cms)` in the CMS): unprefixed utilities in a plugin's stylesheet could override the panel's own, and the CMS's hid the sidebar. `packages/admin/docs/frontend.md` shows the prefixed setup.
- The blueprint and fieldset builder (Structure → Blueprints and Fieldsets, permission `cms.blueprints.manage`): add, edit, reorder and remove fields, nest groups and repeaters, each type's settings; server errors shown on the field they belong to. Collections moved to the Structure group.
- The CMS's admin bundle (`packages/cms`, built with `@imajiner/admin-sdk`), published with `php artisan vendor:publish --tag=sunrice-cms-assets` (also part of `laravel-assets`). `packages/admin/docs/frontend.md` shows how a plugin builds its styles on the panel's.
- Fix: a select's options were stored with repeater row data (`_id`, `_key`, `_hidden`).
- The Collections screens (Content → Collections) with the `cms.collections.view`, `.create`, `.update` and `.delete` permissions; deleting a collection keeps its entries.
- CMS collections and entries: `Collection`, `Entry`, `EntryTranslation` (one per language) and `Revision` models with their tables; `SaveCollection`, `DeleteCollection`, `CreateEntry`, `SaveDraft` (with a version check against overwriting), `PublishEntry` (now, keeping the date, or scheduled), `UnpublishEntry`, `TrashEntry`, `RestoreEntry` and `RestoreRevision` actions; slugs unique per collection and language; the `live()` scope; `config/sunrice-cms.php` with the content languages (`Locales`) and how many revisions to keep. `DeleteBlueprint` refuses a blueprint a collection uses. See `packages/cms/docs/collections.md`.
- CMS fields: blueprints and fieldsets (`sunrice_blueprints`, `sunrice_fieldsets`, `SaveBlueprint`, `DeleteBlueprint`, `SaveFieldset`, `DeleteFieldset`), the field types `text`, `textarea`, `rich_text` (sanitised), `number`, `toggle`, `select`, `date`, `link` (safe URLs only), `media`, `group`, `repeater`, `flexible` and `fieldset` includes, `Schema` (validate, normalise, hydrate, references), `DefinitionValidator`, and your own types with `CmsPlugin::make()->fieldTypes()` (`FieldType`, `CustomField`). The CMS requires `symfony/html-sanitizer`. See `packages/cms/docs/fields.md`.
- AI tools for every resource and settings section: `list_records`, `get_record`, `save_record` (partial updates), `delete_record`, `run_action`, `get_settings`, `update_settings`, plus `list_media` and `get_activity`, with the screens' permissions and validation (now in the `SaveRecord` and `UpdateSettings` actions).
- Fix: read-only AI tokens could still use permissions granted through roles (spatie/laravel-permission's gate check answered first); the read-only check now always runs first.
- AI access: tokens (read-only, expiring) on the AI access page, the MCP endpoint (`/mcp`, laravel/mcp) where AI agents work as the token's user with that user's permissions, `get_panel_info`, and `$panel->tools()` / `aiInstructions()` for plugins' tools (`Sunrice\Admin\Ai\Tool`). Read-only tokens may only view. Changes are logged as the AI agent's; token events are security events and alerts; Users → Revoke AI tokens. See `packages/admin/docs/ai.md`.
- Security alerts by email: an account locked, password spraying, a powerful account signing in from a new address or after a long absence, someone gaining power over users or roles, a dangerous upload, bursts of exports or deletes. Sent to super admins and configured roles and addresses, once per cooldown (`security.alerts`). The `ActivityRecorded` event. See `packages/admin/docs/security.md#email-alerts`.
- Responding to an account in the wrong hands: Users → Sign out everywhere, Lock account and Unlock account (also `sunrice:unlock`), a Locked column, and `AccountGuard` in code. Locked accounts can't log in, and their open sessions end on the next page. Resources gain `Action::visible()` and `Column::state()`.
- Security events in the activity log (source "security"): logins in, out, failed, refused and blocked, accounts locked, password resets, blocked uploads, exports, and changes of roles and permissions. `SecurityLog` for your own, the `SecurityEventRecorded` event, and `security.log_channel` to copy them to a log channel. See `packages/admin/docs/security.md`.
- The activity log: who changed what (resources, users and roles, settings, media), with the fields that changed but never their values, the source (admin, AI agent, system, security) and IP. `ActivityLog::record()` / `updated()` / `withSource()` / `withoutLogging()` for plugins, the Activity log page (`sunrice.activity.view`) with filters and item histories, and `sunrice:activity-prune` (daily, `activity.keep_days`). New `TrashMedia` action. See `packages/admin/docs/activity.md`.
- The `MediaPicker` form field: choose media from the library (folders, search, upload) in resource and settings forms; one id or an ordered list, limited to types. `Media::whereTypes()`. The picker's JSON endpoint `GET /admin/media/picker`, and JSON answers to uploads that ask for them.
- The Media page: folders, upload by drop or picker with progress, search, type filter, details (title, alt text, caption), replace, move, trash and restore. Permissions `sunrice.media.view`, `.upload`, `.update` and `.delete`; `$panel->mediaLibrary(false)` turns it off. `UpdateMedia`, `MoveMedia`, `SaveMediaFolder` and `DeleteMediaFolder` actions. The workbench links its storage and serves at 127.0.0.1:8000.
- Media library storage: `Media` and `MediaFolder` models, `UploadMedia`, `ReplaceMedia` and `DeleteMedia` actions, image sizes (Intervention Image, on the queue if you like) and `sunrice:media-sizes`. Uploads are checked for allowed types, scripts and web pages (by content too) and unsafe SVGs. Config under `sunrice-admin.media`. See `packages/admin/docs/media.md`.
- Settings: sections of typed settings (`Settings` classes with typed properties and defaults, `#[Encrypted]` for secrets), read with one cached query, edited on the panel's Settings page with a permission per section (`$panel->settings()`), and the `SettingsSaved` event. A `Secret` form field. `Field::validationRules()` takes a null record outside resources. See `packages/admin/docs/settings.md`.
- Users and Roles screens (resources under Administration, permissions `sunrice.users.*` and `sunrice.roles.*`), with `PermissionRank`: nobody can manage users or roles with permissions they don't have, delete themselves or change their own roles. Swap or remove them with `$panel->userResource()` and `$panel->roleResource()`. See `packages/admin/docs/users.md`.
- Resources: `Resource::can()` (refuse more than the policy or permissions), `Resource::newRecord()`, `Password` and `CheckboxList` fields, `->disabled()`, `->loadUsing()` and `->saveUsing()` on fields, to-many relationship columns, and filter options from a closure. The panel's own permissions are listed before the app's and the plugins'.
- Resources: admin screens for Eloquent models described in PHP (forms with sections and six field types, lists with search, filters, sorting, row and bulk actions and CSV export), authorized by the model's policy or the resource's permissions. See `packages/admin/docs/resources.md`.
- Roles and permissions with spatie/laravel-permission: its tables ship with the panel, permissions sync from code (`sunrice:sync-permissions`, also after every migrate), a super admin role that may do everything, and `sunrice:make-admin` for the first admin. See `packages/admin/docs/permissions.md`.
- Signing in: login (with remember me), logout and password reset pages; only accounts with `sunrice.access` get in; three-way brute-force throttling (`config/sunrice-admin.php`) and the `LoginThrottled` event. See `packages/admin/docs/auth.md`.

Plugin pages in React with `@imajiner/admin-sdk` (shared React/Inertia/UI, bundles loaded per page, runtime version check). See `packages/admin/docs/frontend.md`.
